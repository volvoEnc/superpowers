# Spec: Углубление воркфлоу superpowers (Claude-вариант)

**Дата:** 2026-06-23
**Ветка:** `chore/workflow-deepening`
**Цель-плагин:** `plugins/superpowers-claude/` (установленный Claude Code вариант)
**Статус:** на ревью

## Goal

Усилить персональный воркфлоу superpowers по двум направлениям, заявленным human partner:

1. **Глубже элиситация** — brainstorming должен задавать больше и более многоугловых вопросов до дизайна (сейчас «один вопрос за раз», decision pack из 7 секций).
2. **Опора на встроенные механизмы Claude Code** — `/code-review`, `/security-review`, `/simplify`, `verify`/`run`, встроенный **Workflow-инструмент** — которых сейчас нет ни в одном скиле.

## Решения (decision pack)

| Измерение | Решение |
|---|---|
| Объём раунда | **Quick-wins + Core** (ambitious-перепись plan-review/writing-plans на Workflow — отложена) |
| Глубина элиситации | **Адаптивно по риску** — полная ширина авто-включается для нетривиальных/рискованных задач; простые остаются лёгкими через тег `NOT-APPLICABLE` |
| Workflow-инструмент | **Паттерны + opt-in** — решающая таблица + opt-in паттерны; ручной диспатч субагентов остаётся дефолтом; прототип на одном реальном плане до любого «дефолта» |
| Гейты ревью | **По риск-тирам** — `/code-review` (medium) всегда перед finishing; `/security-review` только на Tier-1; per-task ревью только для рискованных задач |
| Прецедент при конфликте ревью | Ручное суждение > авто-находка; при настоящем противоречии — спросить human partner (дефолт, в доктрине) |
| Целевой плагин | Только `superpowers-claude/`. Синк в Codex-вариант `superpowers-personal/` — вне объёма (опционально позже) |

## Scope

### In scope (Quick-wins + Core, ~15 правок по ~9 скилам + 1 новый doc)

**Quick-wins (S):**
1. `brainstorming` — батч 2-4 **независимых** вопросов одним вызовом `AskUserQuestion`; один-за-раз остаётся дефолтом для зависимых/последовательных уточнений. **Правило независимости:** вопросы независимы, если ответ на один не меняет формулировку/смысл другого (напр. goal + success-metrics + constraints — батч); если ответ ветвит следующий вопрос (зависимый) — по одному. Дать 1 пример пары независимых и пары зависимых.
2. `finishing-a-development-branch` — после проверки тестов: гейт `/code-review` (medium) на диффе ветки; критичные находки → стоп и фикс; плюс `/security-review` если задеты Tier-1 области. Результат в преамбуле меню завершения.
3. `verification-before-completion` — структурированная строка сбора доказательств перед любым заявлением о готовности (счётчики тестов/exit code, diff stats, вердикт ревью).
4. `test-driven-development` — в фазе REFACTOR опциональная заметка: после green можно прогнать `/simplify`, затем подтвердить, что тесты зелёные. `/simplify` = только качество, не поиск багов.
5. `requesting-code-review` — секция «встроенное `/code-review` vs субагенты-ревьюеры» со ссылкой на доктрину; лестница effort (low рутинно → medium рискованно → high+ пред-мердж); `--comment` / `--fix` (только после ручного одобрения).

**Core (M/S):**
6. `brainstorming` — секция **Question Taxonomy** (Goal, Scope, Non-Goals, Constraints, Success Metrics, Error Handling, Data Model, Security, Performance, UX, Edge Cases, Rollout/Verification); decision pack расширяется до этих измерений с тегом `DECIDED | TBD | NOT-APPLICABLE`. Для простых задач заполняются только релевантные, остальные → `NOT-APPLICABLE` (адаптивность).
7. `brainstorming` — Question Strategist обязан мапить блокирующие неизвестные на измерения таксономии и возвращать: покрытые измерения, следующее измерение, почему важно. Это форсит ширину; в паре с батчингом orchestrator может спросить несколько покрытых измерений сразу.
8. `brainstorming` — **опциональный многоугловой анализатор** (6-8 линз: security, performance, data-integrity, UX, maintainability, failure-modes, cost/scale, ops-complexity), не более одной блокирующей проблемы на линзу + кросс-вопросы, которые питают план вопросов; результат в новую таблицу «Risk Dimensions» в decision pack. **Авто-включается по риску** (адаптивно), на простом — пропускается. **Триггер:** задеты Tier-1 области ИЛИ >1 независимая подсистема/много блокирующих неизвестных ИЛИ human явно просит глубокий разбор. На мелких изолированных изменениях — пропуск.
9. **Новый doc** `plugins/superpowers-claude/docs/review-integration-doctrine.md` — единая модель: `/code-review` + `/simplify` = автоматическая гигиена (баги, мёртвый код, стиль); ручные субагенты = суждение (архитектура, намерение, домен); `/security-review` = риск-тированный гейт; `verify`/`run` = поведенческое подтверждение. Дерево решений + лестница effort + правило прецедента. Остальные правки ревью ссылаются на этот doc.
   - **Важно:** `/code-review`, `/security-review`, `/simplify`, `verify`, `run` — это **встроенные** механизмы Claude Code, НЕ скилы superpowers. Ссылаться на них как `/code-review` и т.п., **без** префикса `superpowers:`.
   - Doc — простой reference-файл (не SKILL.md); лежит в `docs/` внутри плагина, лоадером скилов не загружается (нужно создать каталог `docs/`).
10. `verification-before-completion` — секция **Security-Review Risk Tiers** (единое определение, переиспользуется в `executing-plans` и `finishing`):
    - **Tier 1 (обязателен `/security-review`):** auth/authz, криптография, секреты, внешние API-ключи, выполнение shell, права доступа к файлам, SQL/DB операции, экспорт данных.
    - **Tier 2 (опционально):** крупные рефакторы, изменения конфигурации.
    - **Tier 3 (пропуск):** доки, UI-текст, только-тесты.
    - **Смешанные изменения:** действует высший применимый tier. SQL/DB: мутации/DDL/экспорт = Tier-1; чисто read-only — по контексту (по умолчанию не Tier-1).
    *(Список — предложение по умолчанию; human partner подтверждает под свою модель угроз.)*
11. `verification-before-completion` — отделить командную верификацию (тесты/линт) от поведенческой: для user-visible изменений также `verify`/`run` (запуск приложения). Не применять к докам/чистой логике.
12. `subagent-driven-development` — в per-task цикл вшить риск-тированное встроенное ревью: после quality review — `/code-review` (low, по живому диффу) + `/simplify`; `/security-review` только для задач Tier-1. Встроенное ревью — дефолт для механического качества; ручные субагенты — для суждения. Опционально-по-риску, чтобы крупные планы не жгли бюджет.
13. `dispatching-parallel-agents` — секция-решающая-таблица «ручной Task-диспатч vs Workflow-инструмент» (Workflow: однородные домены, уверенные схемы результата, без human-input в середине; ручной: гетерогенные задачи, неясная форма результата, нужны прерывания) + 1-2 opt-in паттерна. Явно: текущий ручной подход не неправильный.
14. `writing-skills` — пред-деплой чек-лист качества скила: (1) `/code-review` по SKILL.md на противоречия/расплывчатость; (2) `/security-review` если скил трогает auth/секреты/права; (3) минимум один адверсариальный pressure-test ПОСЛЕ правок, доказывающий закрытие лазейки; для правок существующих скилов — сначала прогнать исходный сценарий как baseline.
15. `executing-plans` — перед хендоффом в finishing: если план задел Tier-1, запросить одобрение human на `/security-review` по накопленному диффу и передать риск-оценку плана вперёд.

### Out of scope
- Ambitious-перепись `reviewing-plans`/`writing-plans` на детерминированные Workflow (отложено; сначала прототип).
- Синк правок в Codex-вариант `superpowers-personal/`.
- Любые upstream-PR в `obra/superpowers` (CLAUDE.md обра запрещает fork-специфичные изменения).
- Новый отдельный скил для многоуглового анализа (унифицирован как шаг внутри `brainstorming`).

## Принципы дизайна (инварианты)
- **Сохранить модель чистого контекста оркестратора** — встроенные механизмы дополняют, не заменяют её.
- **Адаптивность** — никакой бюрократии на простых задачах (тег `NOT-APPLICABLE`, opt-in по риску).
- **Единый источник риск-тиров** — определить один раз, ссылаться везде.
- **Без дублирования ревью** — автоматика для механики, субагенты для суждения, явный прецедент при конфликте.

## Acceptance criteria
1. `brainstorming` содержит Question Taxonomy, расширенный decision pack с тегами, правило батчинга, дисциплину покрытия измерений у стратега и опциональный многоугловой анализатор; на простой задаче поведение остаётся лёгким.
2a. Создан reference-doc `docs/review-integration-doctrine.md` (встроенные механизмы — без префикса `superpowers:`).
2b. `requesting-code-review`, `finishing-a-development-branch`, `subagent-driven-development`, `executing-plans` ссылаются на доктрину.
3. Единая политика риск-тиров определена в `verification-before-completion` и переиспользуется в `executing-plans` и `finishing`. `executing-plans` имеет конкретный шаг: проверить Tier-1 и запросить одобрение human на `/security-review` перед хендоффом (не только ссылка).
4. `finishing-a-development-branch` имеет гейт `/code-review` (+ `/security-review` по Tier-1) с выводом результата.
5. `verification-before-completion` различает командную и поведенческую верификацию и содержит шаблон сбора доказательств с полями (счётчик тестов, exit code, diff stats, вердикт ревью).
6. `dispatching-parallel-agents` имеет решающую таблицу manual-vs-Workflow; ручной диспатч остаётся дефолтом.
7. `writing-skills` имеет eval-гейт качества скила (вкл. `/code-review` по SKILL.md и адверсариальный pressure-test после правок).
8. `test-driven-development` (REFACTOR) и `subagent-driven-development` (per-task) упоминают `/simplify` с корректным контекстом (только качество).
9. Все правки — только в `plugins/superpowers-claude/`; внутренние ссылки `superpowers:*` целы.
10. Каждый изменённый скил остаётся самосогласованным (без оборванных ссылок/осиротевших секций).

## Testing / eval approach
- Скилы — это код, формирующий поведение (предупреждение CLAUDE.md). Изменения вести через `superpowers:writing-skills`.
- Для ключевых поведенческих правок (особенно элиситации и гейтов) — адверсариальный pressure-test: прогнать сценарий до/после, доказать, что новое поведение срабатывает (например, brainstorming задаёт многоугловой батч; finishing не завершает без `/code-review`).
- Структурная проверка: каждый изменённый SKILL.md валиден, ссылки на доктрину/риск-тиры резолвятся, `claude plugin validate` зелёный, `claude plugin details` показывает 17 скилов.
- После сборки — переустановить/обновить плагин и проверить в новой сессии, что элиситация и гейты работают.
