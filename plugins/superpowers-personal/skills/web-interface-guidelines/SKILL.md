# Аудит веб-интерфейса по чек-листу

Этот скилл прогоняет **уже готовый** UI по своду прод-правил «Web Interface Guidelines» и сообщает нарушения как `file:line`. Свод лежит рядом со скиллом — локальным снапшотом; в сеть скилл не ходит.

## Когда срабатывает, а когда нет

**Срабатывает**, когда тебя просят *проверить, отаудировать, отревьюить* существующий интерфейс или вёрстку: «прогони этот UI по чек-листу», «найди нарушения доступности», «готова ли эта форма к проду», «проверь фокус-состояния и навигацию». Объект — конкретные файлы, которые уже написаны.

**Не срабатывает**, когда нужно *создать или переделать облик с нуля* — выбрать направление, композицию, сделать интерфейс небанальным. Это другой жанр и другой скилл — `superpowers:frontend-design`. Граница простая: `frontend-design` отвечает за *вкус и оригинальность* (творю облик), этот скилл — за *корректность и соответствие чек-листу* (проверяю готовое).

**На грани жанров** запрос вида «собери UI и сразу проверь его» — это не коллизия, а конвейер: сначала `frontend-design` ведёт сборку, затем `web-interface-guidelines` аудитит результат. Каждый скилл отвечает за свою фазу. Поскольку аудит работает по уже существующему артефакту, дождись, пока интерфейс написан, — иначе нечего открывать по `file:line`.

## Как прогнать аудит

Свод правил лежит рядом со скиллом: `references/guidelines.md`.

Разрешай путь относительно каталога этого `SKILL.md`. Если работаешь из корня этого репозитория, fallback-путь такой: `plugins/superpowers-personal/skills/web-interface-guidelines/references/guidelines.md`.

1. **Прочитай свод правил** по этому локальному пути — это единственный источник правил для аудита.
2. **Открой проверяемые файлы UI** (разметка, компоненты, стили) и пройди их по каждому пункту свода.
3. **Зафиксируй каждое нарушение** в формате репорта (ниже).

Правила бери **только** из этого локального свода. Не достраивай чек-лист по памяти и не подменяй его «общими соображениями» — аудит ценен ровно тем, что сверяется с конкретным сводом.

## Формат репорта

Каждая находка — одна строка:

```
path/to/file.tsx:42 — <краткое описание нарушения> (чек-лист: <пункт свода>)
```

- `file:line` — точное место в проверяемом коде (путь и номер строки).
- Краткое описание — что именно нарушено.
- Ссылка на пункт чек-листа — какое правило свода задето.

Если нарушение охватывает диапазон или повторяется — указывай первую затронутую строку и помечай повтор в описании. Группируй находки по измерениям чек-листа (доступность, формы, навигация, гидратация, производительность), чтобы репорт читался.

## Запрет сети (критично)

Источник правил — **исключительно** локальный снапшот по локальному `references/guidelines.md` (а при отключённой shell-инъекции — `references/guidelines.md` рядом со скиллом). Скилл **не** ходит в сеть, **не** использует рантайм-фетч и **не** выдумывает правила по памяти.

Если снапшот **отсутствует или пуст** — не уходи в сеть как фоллбэк и не выдавай аудит за полный. Вместо этого:

- сообщи, что локальный снапшот правил недоступен;
- укажи ожидаемый путь — `references/guidelines.md` в каталоге скилла;
- сошлись на процедуру восстановления снапшота (она описана в спеке форка, раздел «Стратегия снапшота и обновления»; лицензия и атрибуция источника — в `LICENSE.txt` рядом);
- явно оговори, что без снапшота аудит неполон.

## Применимость по стеку

Команда форка работает в плейн HTML/CSS/JS, поэтому часть правил свода — React/Next-специфика. **Размечай их при аудите по содержанию** (сам снапшот идёт verbatim и не помечен): следующие правила применяй **только в React/Next-проектах**, а в плейн HTML/CSS/JS — пропускай:

- навигация через `<Link>` (Cmd/Ctrl+click, middle-click) — React/Next-роутер; в плейн-вёрстке остаётся фреймворк-нейтральная суть про обычные `<a>`;
- глубокий URL-state для stateful-UI через `nuqs` или синхронизацию с `useState` — React/Next-инструменты;
- controlled vs uncontrolled inputs, `value`+`onChange` против `defaultValue` для неконтролируемых — модель управляемых полей React;
- защита от рассинхрона гидратации (hydration) server/client и `suppressHydrationWarning` только там, где он реально нужен — гидратация React/Next.

**Фреймворк-нейтральную суть этих правил применяй везде:** любое значимое stateful-состояние полезно отражать в URL; дата/время — частый источник рассинхрона между сервером и клиентом независимо от стека.

Правило про семантику интерактивных элементов — `<button>` для действий, `<a>`/`<Link>` для навигации, а не `<div onClick>` — остаётся в **общем** наборе и применяется в любом стеке (в плейн-вёрстке `<Link>` в нём вторичен по сравнению с `<a>` и `<button>`).
