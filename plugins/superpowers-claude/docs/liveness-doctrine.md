# Liveness Doctrine

Единая модель обнаружения зависших/мёртвых фоновых субагентов в длинных прогонах superpowers (от спеки до PR). Скилы ссылаются на этот документ, а не дублируют его содержимое.

> **Это встроенные примитивы Claude Code, а не скилы superpowers.** Ссылаемся на них как `TaskGet`, `TaskStop`, `Monitor`, `ScheduleWakeup`, `CronCreate` — **без** префикса `superpowers:`. Префикс `superpowers:` зарезервирован только для скилов этого плагина.

> **Все константы ниже — настраиваемые дефолты (tunable defaults), а не жёсткие контракты.** `T_promote`, `G`, `S_bash`, `max_restarts`, `max_dispatches_total` и лестница `deadline_s` — стартовые значения, которые оркестратор вправе переопределить. Ни один внутренний механизм харнесса не возводится в ранг гарантии: load-bearing-базой служит пассивный wall-clock floor (пол по настенным часам) плюс валидация carryover (§7.1), а всё остальное — оптимизации поверх них.

## Mental Model

Сегодня каждый диспатч — это **синхронный `await` `Task`**, эскалация **только content-triggered** (субагент должен сам *сообщить* `BLOCKED`/concerns), а `state.json` **не несёт поля живости**. Зависший субагент, который просто перестал выдавать токены, блокирует оркестратор бесконечно — обнаружить это нечем.

Доктрина добавляет **триггер по времени/живости рядом** с существующим content-triggered (не вместо него) плюс состояние и подложку мониторинга, делающие детект по времени вообще возможным. Подход — **Tiered Hybrid** (тированный гибрид), три слоя, дешёвый-первым:

- **Синхронный `Task` — дефолт.** Большинство задач остаются как есть: один `Task`, `await`, компактный результат. Дёшево, чистый контекст, ноль накладных мониторинга. Это **не неправильно** для подавляющего большинства ограниченных единиц работы.
- **Промоция в `run_in_background` + мониторинг — исключение.** Включается по точному правилу (§4.2), а не по умолчанию.
- **Wall-clock floor — пассивная страховка, всегда включена.** Гарантированный baseline даже если каждый более «умный» сигнал недоступен.

Правило большого пальца: **синхронность — для механики, фоновый мониторинг — только для риска.** Платим за overhead фонового диспатча только там, где слепота опасна.

## §4 — Tiered Hybrid

### §4.1 Дефолт: синхронный `Task`

Диспатчим один `Task`, ждём, забираем компактный результат. Остаётся **дефолтом**.

### §4.2 Правило промоции (точное)

Задача **ПРОМОУТИТСЯ** из синхронного `Task` в `run_in_background` + мониторинг живости, когда выполнено **любое** из условий на момент диспатча:

- **PR-1 (риск):** задача относится к **Tier-1** по «Security-Review Risk Tiers» из скила `superpowers:verification-before-completion` (auth/authz, крипто, секреты, внешние API-ключи, выполнение шелла, права файлов, мутации/DDL/экспорт БД). Тиры **не переопределяются здесь** — единый источник в `superpowers:verification-before-completion`. Tier-1 — выше ставки и чаще длинные внешние вызовы, которые стоит наблюдать.
- **PR-2 (бюджет длительности):** запланированный оркестратором `deadline_s` для задачи превышает порог промоции `T_promote`. Если `deadline_s > T_promote` — промоутить.

**`T_promote` — дефолт 300 s (tunable).** Это круглый консервативный порог, отделяющий короткие, дёшево-нянчимые единицы от длинных, где синхронный `await` — это немониторируемый риск. Дефолт **не выведен** из какой-либо константы харнесса и **сознательно decoupled** от часто упоминаемого «~300 s окна prompt-cache» (см. §6 и §12.4): даже если окно кэша не подтвердится, дефолт 300 s от него не зависит.

Промоция фиксируется флагом `promoted: true` на записи `inflight` (§8). Если ни одно условие не выполнено — задача идёт синхронно, страховка — только wall-clock floor.

### §4.3 Почему «наблюдаемость» требует `run_in_background`

Синхронный `await` `Task` не отдаёт управление оркестратору, пока не вернётся. Значит **активный мониторинг живости возможен только при неблокирующем диспатче** — то есть `run_in_background`. Промоция и есть акт превращения иначе-немониторируемого длинного синхронного `await` в наблюдаемую фоновую работу.

Существует два фоновых вида, мониторятся по-разному (§5):

- **bg-agent** — промоутнутый `Task`/`Agent` через `run_in_background`.
- **bg-bash** — промоутнутая долгая `Bash`-команда через `run_in_background`, пишущая в output-файл.

### §4.4 Wall-clock floor (пассивный, всегда включён)

Для **каждой** единицы в полёте — промоутнутой или нет — оркестратор штампует timestamp диспатча в `state.json` (`dispatched_at`, §8). **Wall-clock floor** — универсальная, беззависимостная страховка:

- Вычисляется **между задачами** и в **точках пробуждения `ScheduleWakeup`** (§6).
- Единица, у которой `now - dispatched_at` (или `now - last_progress_at`) превышает свой `deadline_s` на **множитель grace** `G`, **подозревается зависшей**.
- **`G` — дефолт 2× (tunable).** Единица подозревается зависшей при `2 × deadline_s` без завершения/прогресса. Двойной запас грейса поглощает нормальную дисперсию (задача, легитимно отработавшая чуть дольше) до запуска рестарта (§10).

Для синхронных (непромоутнутых) задач floor по необходимости **пассивен**: он не может прервать живой `await`, но **может** быть проверен в момент возврата управления (граница следующей задачи) и — критически — **на resume после компакции**, где он единственный сигнал живости, переживающий компакцию. Floor — это baseline graceful-degradation: даже если каждый «умный» сигнал §5 недоступен, wall-clock floor всё равно работает.

> **Стыковка.** Фоновый yield независимого веера (N ≥ 2) делит механику `run_in_background`/`inflight` с промоцией §4.2, но триггерится интерактивностью, а не риском — см. `dispatch-yield-doctrine.md`.

## §5 — Detection Signals (по видам)

У каждого вида в полёте — основной сигнал и задокументированный fallback.

### §5.1 bg-agent (промоутнутый `Task`/`Agent`)

- **Основной:** harness **stall-watchdog** — предположительно зависший фоновый агент всплывает как failed-with-partial по таймауту столла.
- **⚠ Это оптимизация, а не контракт — НЕ подтверждено.** Точное имя env-переменной, дефолт и сама *гарантия* того, что стол всплывёт как ловимый failure-with-partial, **надёжно не задокументированы** (см. spike-findings §12.1: вердикт UNCONFIRMED — нет CLI-флага, env-дамп заблокирован, упоминания в репо самоссылочны). Доктрина **не вправе** трактовать watchdog как жёсткий контракт.
- **Fallback (graceful degradation):** если watchdog не сработал (или его поведение не подтверждено), **wall-clock floor** (§4.4) на `dispatched_at` / `last_progress_at` ловит зависание на `G × deadline_s`. Доктрина работает **с watchdog и без него** — watchdog лишь делает детект *быстрее*.

### §5.2 bg-bash (промоутнутая долгая `Bash`)

- **Основной:** **mtime output-файла (staleness).** Оркестратор читает output-файл bg-bash (`output_path`, §8) и проверяет его **mtime**. Если файл не менялся дольше **окна staleness** `S_bash` (дефолт **120 s**, tunable, и `≤ deadline_s`) — команда подозревается зависшей. Прочитать содержимое для компактной строки-прогресса можно — но **никогда не лить сырой вывод в контекст** (§6).
  - **`TaskOutput` deprecated** — не использовать (в этом харнессе инструмент отсутствует; spike-findings §12.2 CONFIRMED). **Читать output-файл напрямую** через `Read`.
- **Вторичный:** статус `TaskGet` как corroborating-сигнал (`running` против `failed`/`completed`). Использовать, чтобы отличить «медленно, но жив» от «мёртв», а не как единственный триггер. `TaskGet`/`TaskStop` — kind-agnostic по `task_id` (применимы к обоим видам; spike-findings §12.2 CONFIRMED), стандартизируемся на **`task_id`** (deprecated-алиас `shell_id` не использовать).
- **Fallback:** если output-файл отсутствует или никогда не пишется (команда, выдающая вывод только в конце — §10), mtime неинформативен; откат на **wall-clock floor** по `dispatched_at`.

### §5.3 Orchestrator long-run + wall-clock floor

- **Сигнал:** `now - dispatched_at` (и `last_progress_at`) из `state.json`, вычисляемые в **точках пробуждения `ScheduleWakeup`** и **между задачами**. Это сквозной floor §4.4 и **единственный** сигнал, переживающий компакцию и применимый к непромоутнутым синхронным задачам на их следующей границе.

- **`last_progress_at` для bg-agent — двухуровневая схема.** В отличие от bg-bash (где есть mtime output-файла), у bg-agent **нет гарантированного дешёвого сигнала прогресса**:
  - **Если watchdog подтверждён**, всплывший partial может обновить `last_progress_at` и дать позиционный сигнал для гварда §7.3.
  - **Иначе (обычный, консервативный случай — signal-less bg-agent)** оркестратор **не** опрашивает `TaskGet` ради искусственного прогресса — `TaskGet` сообщает состояние живости (`running`/`failed`/`completed`), а **не forward-progress**, поэтому не отличает «медленно работает» от «заклинил». Для signal-less bg-agent `last_progress_at` просто отслеживает `dispatched_at`, floor правит по `now - dispatched_at`, и — как сказано в §7.3 — гвард повтора **не может сработать**, так что `max_restarts` остаётся единственным конечным пределом. Создание более богатого сигнала прогресса для bg-agent — **оптимизация, не требование**; ограниченная деградация приемлема как baseline.

**Сводка деградации:** основные сигналы — оптимизации; wall-clock floor — гарантированный baseline. Ни один недодокументированный механизм не является load-bearing.

## §6 — Watchdog Cadence

### §6.1 `ScheduleWakeup` как backstop-poll

`ScheduleWakeup` — это **примитив уровня оркестратора/главного цикла** (Task-субагенты его не получают — поэтому spike-субагент и не увидел его). Оркестратор планирует пробуждение, чтобы пере-войти и прогнать floor-проверку §4.4 по `state.json`, уважая экономику окна prompt-cache. Эти числа **подтверждены** описанием самого `ScheduleWakeup` в этом харнессе (spike-findings, «Orchestrator review correction»): у prompt-cache TTL ~5 минут (300 s); держаться под 300 s держит кэш тёплым; ровно 300 s выбирать не стоит (worst-of-both).

- **Активный опрос (промоутнутая единица в полёте):** пробуждение **< 300 s** (тёплый кэш, например 60–270 s) — пере-вход дёшев. Именно поэтому `T_promote` и активный poll делят шкалу ~300 s (хотя дефолт `T_promote` от константы кэша decoupled, §4.2).
- **Idle-тики (ничего промоутнутого в полёте):** пробуждение **1200–1800 s** (20–30 мин). Нет смысла жечь тёплые опросы, когда идут только пассивные синхронные задачи; следующая **between-task**-граница всё равно прогонит floor.

Числа помечены как **tunable guidance** (настраиваемые ориентиры). `CronCreate` (poll) и `Monitor` (push) — валидные альтернативы, но `ScheduleWakeup` — первичный примитив.

### §6.2 Between-task checks

На каждой границе задачи оркестратор прогоняет floor-проверку по всем записям `inflight` до диспатча следующей единицы. Это бесплатно (управление уже у оркестратора) и ловит синхронный случай в момент возврата управления.

### §6.3 Опциональный `Monitor` (reactive push) — с правилом чистого контекста

Для лога bg-bash оркестратор **может** прицепить `Monitor`, чтобы получать реактивный пуш при появлении паттерна, вместо опроса. Это **опционально**, не требование.

- **Жёсткое правило — чистый контекст (G6):** `Monitor` (или любое чтение вывода) обязан вынести в оркестратор только **компактную строку-receipt**. **Никогда** не лить сырой вывод bg-bash, полные логи или транскрипты в контекст оркестратора. Извлечь однострочный сигнал прогресса (и обновить `last_progress_at`), затем сырой текст выбросить. Оркестратор остаётся лёгким — это не обсуждается.

## §7 — Response on Hang / Death

**Позиция: максимальная автономия.** Обнаруженное зависание/смерть оркестратор обрабатывает сам везде, где возможно; человек — последняя инстанция.

### §7.1 Restart-fresh с carryover (санитизация + валидация)

При обнаружении (любой сигнал §5):

1. **Остановить мёртвую/зависшую единицу**, если она ещё номинально жива (`TaskStop` по `task_id` для bg-agent/bg-bash, который харнесс ещё не зафейлил).
2. **Спасти, санитизировать и провалидировать partial / receipt** — всплывший partial bg-agent или содержимое output-файла bg-bash **компактится в receipt И санитизируется перед carryover**:
   - **Вычистить** секреты / креды / токены и сырые дампы вывода (sanitize: strip secrets/credentials/tokens). Это **расширяет правило чистого контекста G6** (§6.3) с *чтений* оркестратора на *содержимое carryover*: та же дисциплина «компактный receipt, никогда сырой вывод», что защищает контекст оркестратора, защищает и контекст свежего субагента.
   - **Провалидировать** спасённое. Если partial **повреждён / не парсится / неполон (corrupt/unparseable)** — отметить этот факт и передать вперёд **только валидированный остаток scope** — **не** скармливать мусор свежему агенту. Спасённое (санитизированное) записать в receipt задачи, чтобы ничего не потерялось молча.

   *Замечание (spike-findings §12.5, UNCONFIRMED):* гарантия спасения partial не подтверждена (bg-agent partial завязан на неподтверждённый watchdog; output-файл bg-bash может быть отсутствующим/обрезанным/в середине записи). Поэтому валидация здесь **load-bearing**, а не belt-and-suspenders: при провале спасения — нести только остаток scope.
3. **Пере-диспатчить СВЕЖИЙ субагент** с:
   - **прошлым (санитизированным) partial / receipt**, и
   - **остатком scope** (что осталось доделать), и
   - явной пометкой, что прошлая попытка **зависла/умерла** (чтобы свежий агент не переделывал готовое вслепую и был насторожен к режиму отказа).
4. **Инкрементировать `restarts`** на записи `inflight` (§8) и пере-штамповать `dispatched_at` / `last_progress_at`.

Свежий субагент **свеж** (чистый контекст) по существующему правилу жизненного цикла субагентов — никогда не переиспользовать транскрипт зависшего агента как память.

### §7.2 Щедрая, конечная граница

- **`max_restarts` — дефолт 5 (щедро, tunable).** Рестартим свежим до `max_restarts` раз перед эскалацией. Граница **конечна** — буквально-бесконечного цикла нет — но щедра, потому что транзиентные столлы часты, а раунд-трип к человеку дорог.

### §7.3 Гвард патологического повтора

Эскалировать **до** исчерпания `max_restarts`, если отказ явно **не транзиентный**:

- **Одна задача зависает повторно в той же точке.** Если спасённый partial (или последний receipt прогресса) показывает гибель единицы в **том же месте** на ≥ 2 подряд рестартах (тот же шаг, файл, оффсет вывода) — это настоящая глубинная проблема, не флейк. Прекратить рестарты и эскалировать сейчас. Жечь весь бюджет рестартов на детерминированном зависании — пустая трата времени и денег.

**Жёсткое ограничение — гварду нужен позиционный/прогресс-сигнал, и он не всегда есть.** Гвард ключуется на «гибель в **той же точке**», что предполагает сравнимый по-рестартный сигнал: output-файл bg-bash, спасённый partial bg-agent или receipt последнего прогресса. **Когда такого сигнала нет, гвард СРАБОТАТЬ НЕ МОЖЕТ.** Чистейший случай — **bg-agent без watchdog-partial** и без иного дешёвого сигнала прогресса (signal-less, см. §5.1, §5.3): у оркестратора есть только `dispatched_at` для сравнения — он говорит *что* единица превысила бюджет, но **не где** она умерла, так что «та же точка» недетектируема. В этом режиме:

- Короткое замыкание патологического повтора **инертно** — никогда не срабатывает.
- **`max_restarts` (§7.2) становится ЕДИНСТВЕННЫМ конечным пределом** (sole bound) живостных рестартов для этой единицы. Прогон всё равно завершается (эскалирует в `human-decision-required` по исчерпании `max_restarts`), но лишь после полного бюджета рестартов, а не рано.

Это **задокументированная ограниченная деградация (documented bounded degradation)**, не дыра: худший случай для signal-less bg-agent — `max_restarts` свежих диспатчей перед эскалацией, а не ранний обрыв. Добавление дешёвого сигнала прогресса для bg-agent (чтобы гвард *мог* сработать раньше) — оптимизация (§5.3).

### §7.4 Эскалация к человеку — последняя инстанция

Эскалировать к человеку **только** когда:

- `max_restarts` **исчерпан**, **ИЛИ**
- сработал **гвард патологического повтора**.

Эскалация переиспользует существующий словарь: записать `human-decision-required` (существующий исход эскалации `superpowers:subagent-driven-development` / `superpowers:executing-plans`) в `state.json` и receipt задачи, затем **остановиться (halt)**, а не крутиться. Живостная эскалация — просто новая **причина**, питающая существующий канал эскалации, а не параллельный.

### §7.5 Composition с content-triggered лимитами

Триггер по времени/живости **аддитивен и ортогонален** content-triggered лимитам:

- **Content-triggered (существующий):** субагент *возвращает* `BLOCKED` / review-issues → засчитывается в per-task пул **max-2-fix-attempts**; разделение `implementation-wrong` против `plan-wrong` без изменений.
- **Time/liveness-triggered (новый):** субагент *не возвращается* вовремя → засчитывается в отдельный пул **`max_restarts`** с гвардом патологического повтора.

**Два пула независимы (independent).** Живостный рестарт (агент ничего не сообщил) — иной класс отказа, чем fix-attempt (агент сообщил о проблеме); смешение позволило бы склонной к зависаниям задаче молча исчерпать fix-бюджет или наоборот. Оба в итоге сходятся в один исход эскалации `human-decision-required`, но считаются **раздельно**. Content-эскалация `plan-wrong` по-прежнему **останавливает прогон немедленно** (существующее правило); живостная эскалация останавливает затронутую задачу и репортит.

**Правило композиции (как два пула комбинируются для одной задачи).** Независимость сама по себе оставляет щель по тратам токенов: задача могла бы прожевать весь живостный бюджет рестартов *и* весь fix-бюджет до эскалации. Поэтому пулы композируются по явному per-task правилу. Одна задача эскалирует в `human-decision-required`, когда выполнено **любое**:

- **content-triggered** пул исчерпан (существующий per-task лимит **max-2-fix-attempts**), **ИЛИ**
- **liveness** пул исчерпан (`max_restarts`, §7.2), **ИЛИ**
- **сумма** свежих диспатчей из *обоих* пулов пересекла **комбинированный per-task потолок свежих диспатчей** `max_dispatches_total`.

- **`max_dispatches_total` — дефолт `max_restarts + max_fix_attempts` (5 + 2 = 7), tunable.** Это кэпит **общее** число свежих диспатчей субагентов, которое одна задача может вызвать через оба класса отказов, чтобы суммарные траты токенов на задачу были ограничены даже когда задача попеременно зависает и репортит concerns. Считается дёшево: счётчик `restarts` (§8) плюс существующий счётчик fix-attempt дают per-task сумму диспатчей; когда сумма достигла потолка — эскалировать независимо от того, исчерпан ли любой отдельный пул.

Per-pool лимиты и комбинированный потолок все три enforced; что связывает первым, то и триггерит эскалацию. **Additive only:** ничего из существующих лимитов не удаляется и не ослабляется — независимость пулов сохраняется для *атрибуции*, а потолок ограничивает *суммарные* per-task траты.

## §8 — state.json fields (ссылка, не переопределение)

Поля живости — `inflight[]` (массив), per-task `deadline_s`, `promoted`, `dispatched_at`, `last_progress_at`, `output_path`, `restarts`. **Формы полей определены один раз в `superpowers:phase-handoff` → `## State JSON`; здесь не переопределяются.** Здесь — только как они работают:

- **`inflight`** — массив (батч может диспатчить несколько единиц; §10). Запись **удаляется**, когда единица завершилась и её receipt записан, так что непустой `inflight` на resume == «что-то было в полёте».
- **`deadline_s`** — per-task, назначается по риск-тиру на диспатче. Дефолтная лестница (**tunable**, оркестратор может переопределить per task): Tier-3 `120`, Tier-2 `300`, Tier-1 `600`. Это бюджет, с которым сравнивают wall-clock floor (§4.4) и правило промоции (§4.2).
- **`promoted`** — пошла ли единица в фон+мониторинг.
- **`restarts`** — живостный пул (§7.2), **явно отдельный** от content-triggered max-2-fix-attempts пула.
- **`last_progress_at`** — инициализируется значением `dispatched_at`, обновляется на любом сигнале прогресса; для sync/signal-less bg-agent просто отслеживает `dispatched_at`.

**Compaction survival:** непустой `inflight` на resume == проверить/перезапустить. Восставший оркестратор читает `state.json`, видит непустой `inflight`, и для каждой записи считает `now - dispatched_at` / `now - last_progress_at`; если превышает `G × deadline_s` — заключает «в полёте слишком долго → check/restart» и входит в путь ответа §7. Это и есть механизм, превращающий «оркестратор умер/скомпактился в полёте» из тихой потери в детектируемое восстановимое событие. Зеркалит существующее правило resume («восстанавливаться из `state.json` на диске, а не из чата»).

## §10 — Edge Cases

- **Compaction mid-flight.** Оркестратор компактится/умирает, пока единица в полёте. Обрабатывается §8: непустой `inflight` + устаревший `dispatched_at` на resume → check/restart. Это заглавный кейс восстановления.
- **Restart storms.** Флапающая задача повторно зависает. Ограничена `max_restarts` (§7.2) **и** короткозамкнута гвардом патологического повтора (§7.3). Счётчик `restarts` durable в `state.json`, так что шторм не сбросится прятанием счёта в чат. Батч промоутнутых единиц не должен крутиться независимо: floor-проверка обрабатывает весь массив `inflight` за пробуждение, а конечная per-entry граница кэпит суммарную работу рестартов.
- **Легитимно долгий промоутнутый юнит.** Грейс `G`=2× (§4.4) плюс риск-адекватный `deadline_s` (§8) поглощают честные долгие прогоны; `last_progress_at` (обновляемый из сигналов прогресса / mtime) означает, что задача, *делающая прогресс*, **не** убивается лишь за превышение `deadline_s` — подозревается только задача, что и over-budget, **и** без прогресса. Tunable: поднять `deadline_s` для известно-медленной единицы на диспатче.
- **Watchdog отсутствует / иной.** Graceful degradation (§5.1): wall-clock floor всё равно ловит зависание на `G × deadline_s`. Доктрина никогда не *требует* watchdog.
- **bg-bash без вывода.** Staleness mtime неинформативна (fallback §5.2) → правит wall-clock floor по `dispatched_at`. Опционально доктрина рекомендует промоутнутым bg-bash-командам эмитить периодическую heartbeat-строку в output-файл, чтобы mtime оставался осмысленным (рекомендация, не жёсткое требование — zero-dep).
- **`parallel()` / `pipeline()` со stuck-агентом — ловится на уровне батча (mitigated), внутренняя атрибуция вне scope.** **Мёртвый** субагент внутри Workflow всплывает как `null` в агрегатор (уже обработано). **Stuck** (живой-но-зависший) агент внутри `parallel()`/`pipeline()` иначе блокировал бы свой батч **невидимо**, потому что Workflow владеет этим fan-out и у оркестратора нет записи `inflight` *на каждого* внутреннего агента. **Митигация (реальная, не advisory):** оркестратор штампует **ОДНУ запись `inflight` для самого ВЫЗОВА Workflow** перед инвокацией —
  - `kind: "bg-agent"`,
  - `deadline_s` = **сумма** внутренних бюджетов для `pipeline()` (стадии идут серийно) / **max** внутренних бюджетов для `parallel()` (агенты конкурентны), умноженная на грейс `G` при вычислении,
  - `dispatched_at` штампуется на вызове.

  Wall-clock floor (§4.4) тогда ловит **wedged-батч как единицу**: если вызов Workflow не вернулся к `G × deadline_s` — подозревается зависшим и входит в путь ответа §7 (остановить вызов, спасти что есть у агрегатора, пере-диспатчить). **Residual limitation сужена:** ловим *что* батч завис, но **не какой** внутренний агент — рестарт на гранулярности батча; для тонкого восстановления предпочтителен ручной `Task`-диспатч (per-agent `inflight`, полностью покрыт доктриной).
- **False-positive kill почти-готового юнита.** Если единица завершилась между решением floor «подозреваю зависшей» и `TaskStop`, спасённый результат — всё равно настоящий результат: сверять output/receipt перед отбрасыванием и де-дуплицировать против результата свежего рестарта (carryover scope должен сделать свежего агента no-op'ом, если работа реально была закончена).
